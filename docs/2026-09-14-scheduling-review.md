# 时间调度与架构审查

## 项目目的与实现现状

初始设计的目标是纯前端中文日计划工具：围绕 Google Calendar 的固定承诺，根据任务最小时长、期望时长、优先级、截止时间、场景和依赖调整一天的安排。普通日历事件受到保护，计划经用户发布后同步。

`CONTEXT.md` 扩展了 Weekly Plan、Cross-day Task 和 Daily Share 的领域语言。但实际 `scheduleDay` 接收的是日任务列表，尚无周分配与跨日进度模块。因此本次改善日计划的正确性，不将领域术语的存在视为周计划已经实现。

## 本次已修复

| 问题 | 原来的行为 | 修改后 |
| --- | --- | --- |
| 重叠场景重复计量 | 工作和居家各有 09:00–10:00，容量显示 120 分钟，90 分钟最低需求被误判为放置失败 | 物理容量是 60 分钟，直接提示最低需求超出容量 |
| 同场景窗口人为碎片化 | 09:00–10:00 与 09:30–10:30 无法容纳不可拆分的 90 分钟任务 | 合并同场景重叠或相邻区间，可连续安排 09:00–10:30 |
| 日计划使用次日容量 | 23:00–次日 02:00 被全部计入今天 | 裁剪至计划日的次日零点，只有 60 分钟可用 |
| 冲突缺少调整量 | 只列可用和所需时长 | 同时显示缺口分钟数与可执行的调整方式 |
| 概览缺少结果指标 | 主要展示想要时长、最小时长和容量 | 增加已安排、比想要时长少多少、剩余空闲；解释空闲仍受场景等约束 |

## 已落地的模块调整

`availability.js` 提供单一接口 `buildDayAvailability`，集中处理日期范围、调度起点、停用块过滤、同场景区间合并、受保护区间扣除和物理容量计算。它返回可放置区间及去重后的容量，不修改输入，不涉及 DOM、存储或日历请求。

不同场景的重叠区间仍分别保留，避免改变任务的场景准入规则。总容量按时间区间并集计算；各场景仍在调度器共享的剩余时间池中放置。通用 `totalMinutes` 保持原来的求和语义，避免影响其他调用方。

`scheduleDay` 使用这一模块准备输入并负责分配、放置与约束校验。结果汇总由调度结果计算；界面直接呈现结果，不自行重复推算容量和压缩量。

## 后续问题与优先级

以下是实现审查发现的限制或待验证风险，不属于本次已修复范围。

1. **跨窗口依赖与回填需要专项回归。** `scheduleWindow` 返回的依赖结束时间来自初次放置，但返回的任务片段可以来自回填后的计划。两份数据可能不同；最终依赖校验能拒绝错误顺序，但可能把本可调整的情况变成冲突。应先构造发生任务结束时间变化的最小跨窗口用例，再使依赖结束时间从最终片段统一派生。
2. **场景顺序不等于任务依赖顺序。** `orderedContextsForDependencies` 将任务依赖投影为场景依赖；合法的“工作 A → 居家 B → 工作 C”可能产生场景环，并退回默认顺序。长期应在共享可用区间上按任务依赖选择可放置任务，使场景成为任务资格约束，而不是整批执行的顺序。
3. **浮动任务只能选择一个窗口。** 即使任务允许拆分，跨多个场景合计足够、每个场景都不足时，当前窗口分配模型仍可能失败。与上一项一起处理，避免分别增加局部补丁。
4. **存在阻塞整个草案的规则。** 过期截止时间或无效依赖使整个日计划返回冲突，这是当前明确的产品规则。后续可设计“保留可执行任务、显式列出阻塞任务”的部分计划模式，但应同时定义发布行为，避免用户误以为所有任务已安排。
5. **界面模块责任过多。** `ui.js` 同时管理状态、任务编辑、日历合并、同步操作与 DOM。下一步适合将草案状态变更收拢到纯函数模块，让渲染和 Calendar 适配器使用相同的状态转换结果。
6. **周计划应独立于日内放置。** 若实现周计划，先由周分配模块产生 Daily Share，再输入日计划模块；不要复制跨日任务，也不要将周分配加入 `scheduleDay` 的放置循环。
