# 按场景窗口隔离调度 Design

Date: 2026-07-09

## 背景与问题

现有调度器 `scheduleDay` 用一个**全局**的 `allocateDurations` 把当天全部富余时间(可用总量 − 全部任务最小时长之和)按 `优先级 × 弹性空间` 分配给所有任务,不区分任务落在哪个场景窗口。

这导致两个窗口互相输送富余,产生不合理结果。真实复现(2026-07-09 用户数据):

- 可用块:工作 10:15–16:30,下班后 17:20–23:00。
- 上午一个工作任务("MT tef1002")实际完成时间延长,压缩了工作窗口容量。
- 但全局分配把大量富余集中给了下班后窗口里优先级最高的"莉莉安娜"(想要 90 / 最小 60),使其膨胀到 90 分钟,撑爆下班后窗口。
- 结果最低优先级的"开车"(下班后,最小 15)只剩 11 分钟可放 → 报冲突 `placement_failure`。

即"工作时间任务延长却导致晚上任务块被挤掉",违反直觉。

此外定位到一个独立 bug:窗口内压缩函数 `distributeCompression` 在**一轮凑不齐缺口**时直接返回 `null` → 立即报冲突,丢弃了本可先压下的部分 slack(实测差一分钟就放弃),缺少跨轮收敛。

## 目标

1. **场景隔离**:仅工作任务只在工作窗口内竞争,仅下班后任务只在下班后窗口内竞争,两窗口的富余时间互不输送。
2. **任意场景任务择优**:对每个窗口各生成一份计划,比较总压缩量,择优采用。
3. 顺带修复窗口内压缩的部分收敛 bug。
4. 不破坏现有行为与测试。

## 概念定义

- **窗口 (window)**:按可用块的 `context` 分组。所有 `work` 块构成工作窗口,所有 `home` 块构成下班后窗口。若出现 `any` / `custom` 块,各自成窗口。窗口容量 = 该场景全部块的分钟数之和(已扣除受保护事件、已完成段、当前时刻之前部分)。
- **专属任务 (dedicated)**:仅与一个窗口兼容(如仅工作 / 仅下班后任务)。锁定到该窗口。
- **浮动任务 (floating)**:与两个及以上窗口兼容(如 `any` 场景任务)。需择优分配到某一窗口。
- **固定任务 (fixed)**:用户勾选"固定"且有固定时段的任务。按其固定时段落在哪个窗口的块内归入该窗口,窗口内优先放置;不属于浮动任务的枚举。
- **压缩量 (compression)**:`Σ (effectiveDesired − actualScheduled)`,对所有已排任务求和。越小越贴近想要时长,计划越优。
- **冲突窗口 (conflicted window)**:某任务连 `effectiveMinimum` 都放不下的窗口。

## 架构

### 1. 抽出窗口内调度核心 `scheduleWindow`

将现有 `scheduleDay` 中"分配时长 → 放置固定/弹性任务 → 压缩重试"的 `while` 循环整体抽成纯函数:

```
scheduleWindow({ tasks, blocks, planDate, now })
  -> { scheduled, unscheduled, failure, compression, allocations }
```

- 仅使用传入的 `blocks`(单窗口容量)与 `tasks`(归属该窗口的任务)。
- 内部沿用现有 `allocateDurations` / `attemptPlacement` / `competingDonors` / `distributeCompression`,语义不变,只是作用域缩小到单窗口。
- `failure` 非空表示该窗口无法容纳某任务最小时长。
- `compression` = 该窗口内 `Σ(effectiveDesired − actual)`。

### 2. 修复窗口内压缩的部分收敛

`distributeCompression`:当某一轮活跃让渡者的 slack 不足以覆盖剩余缺口时,不再直接返回 `null`,而是**先压下当前可得的全部 slack**(`break` 出循环),返回已压下的部分。外层 `while` 循环据此再重试一轮、缺口变小后继续压缩下一批让渡者,直至放下或确实无 slack 可压(此时返回 `null` → 冲突)。收敛性由"每轮至少压下 1 分钟、slack 单调递减"保证。

### 3. 浮动任务择优分配(路线甲 + 阈值退化)

在 `scheduleDay` 主流程中:

1. 划分窗口,分类任务(固定→按时段归窗口;专属→唯一窗口;浮动→候选窗口集合)。
2. **若浮动任务数 ≤ 8(阈值)**:枚举每个浮动任务落其候选窗口的所有组合(路线甲)。
3. **若浮动任务数 > 8**:退化为路线乙贪心——专属/固定任务先各窗口排好,再按优先级逐个把浮动任务试放各候选窗口,选"新增压缩最少"者落下。
4. 每种组合下,每个窗口独立跑 `scheduleWindow`,汇总:
   - `conflictCount` = 冲突窗口数;
   - `totalCompression` = 各窗口 `compression` 之和。
5. **择优顺序**:`conflictCount` 升序 → `totalCompression` 升序 → 优先级加权兜底(保证确定性、可复现)。
6. 选出最优组合,合并其各窗口的 `scheduled` / `unscheduled` / `durationPlan` 作为结果。

### 4. 全局前置检查(保留)

`scheduleDay` 开头保留现有全局检查:
- 固定任务的截止时间违反 → `deadline_violation`(不变)。
- 自动锁定任务违反截止时间 → 自动解锁(不变)。

去掉原来的全局 `requiredMinimum > availableMinutes` 粗检不再作为唯一判据——真正的可行性由各窗口内 `scheduleWindow` 判断(用户的原始 bug 正是全局够、窗口紧)。但可保留它作为一条快速的、必然冲突的早退路径(全局都不够则必定冲突)。

### 5. 冲突输出

最优组合仍有冲突窗口时,报 `placement_failure`,`belowMinimum` 指明放不下的任务及其候选块信息(沿用现有结构)。

## 数据流

```
scheduleDay
  ├─ 前置:completed / blocked / deadline 检查(不变)
  ├─ 划分窗口(按块 context)
  ├─ 分类任务(fixed / dedicated / floating)
  ├─ 枚举浮动分配(≤8 路线甲 / >8 路线乙)
  │    └─ 每组合:各窗口 scheduleWindow → 汇总 conflictCount / totalCompression
  ├─ 择优组合
  └─ 合并结果(segments / unscheduled / durationPlan)
```

## 边界情况

- **单窗口**(全部块同一 context,或全 `any`):无浮动分配决策,退化为当前全局行为 → 现有测试不回归。
- **浮动任务在所有窗口都放不下**:各组合均冲突,择优取"冲突最少",最终仍报冲突并指明任务。
- **`any` 块 + 具体块并存**:`any` 块自成窗口,导致仅工作/仅下班后任务也与 `any` 窗口兼容而成为浮动任务——由枚举正常处理(一个工作任务确实可用 `any` 块),可接受。
- **固定时段跨窗口或不在任何块内**:沿用现有 `placeFixedTask` 行为(放不下则该任务失败)。

## 测试策略(TDD)

1. **用户精确场景**(2026-07-09 数据):`status: ok`,开车 ≥ 最小 15,工作/下班后任务不串窗口。
2. **场景隔离**:延长工作窗口内某任务(减少工作容量),下班后任务的实际分配不变。
3. **任意任务择优**:构造两窗口松紧不同,验证任意任务落到"压缩更少"的窗口。
4. **部分压缩收敛**:构造单窗口内需多轮压缩才收敛的场景,验证不再误报冲突。
5. **阈值退化**:浮动任务 > 8 时走贪心路径(可通过可注入阈值或独立测试贪心函数验证)。
6. **回归**:现有全部测试保持绿。

## 应用结构影响

改动集中在 `src/scheduler.js`:
- 新增 `scheduleWindow` 纯函数(抽取现有循环)。
- 新增窗口划分 / 任务分类 / 浮动枚举 / 择优的编排逻辑。
- 修改 `distributeCompression` 的收敛行为。
- `scheduleDay` 主流程改为窗口编排。

`priority.js` / `models.js` / `ui.js` 不需改动(冲突输出结构不变)。

## 验收标准

- 用户 2026-07-09 场景不再误报冲突,排程合理。
- 工作窗口与下班后窗口富余互不输送。
- 任意场景任务按总压缩量择优落窗口。
- 窗口内压缩可跨轮收敛,不再"差一分钟就放弃"。
- 现有测试全绿,新增测试覆盖上述行为。
