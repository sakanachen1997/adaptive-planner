# Adaptive Planner 

Adaptive Planner 是一个中文日程规划应用。它会根据当天可用时间、任务权重、最短执行时长、截止时间、任务类型、精力需求、工作或居家场景，以及 Google Calendar 中已有的固定事件，重新安排当天仍可调整的任务。

## 调度模型

页面中的 `调度` 按钮会重新计算当天计划。系统不会把“想要时长”当成必须满足的承诺，而是把它作为权重参数之一。

每次调度都会为任务计算实际时长：

- `想要时长`：参与优先级和弹性空间计算。
- `最小时长`：硬下限，实际时长不能低于它。
- `实际时长`：系统根据可用时间、重要性、deadline、任务类型、精力匹配和弹性空间计算出的排程时长。

任务类型只是一组表单预设，不是用户不可见的隐藏绑定。选择任务类型会把执行场景、精力需求、体力需求、顺序偏好、是否可拆分、最小分段时长、外部承诺填入表单；这些字段都会显示在添加/编辑任务菜单里，用户可以随时覆盖，保存时以当前表单值为准。“前置任务”以复选框列出其他任务，可以直接勾选一个或多个，用来声明当前任务必须等哪些任务全部完成后才能开始。

可用时间块可以选择“工作时间”“下班后”“任意时间”或“自定义”。自定义时间块最多 8 个，选择“自定义”后会出现名称输入框，可以命名为 A、B 等；这些名称随后会出现在任务的“执行场景”选项中。名称与内部稳定 ID 分离，因此重命名 A 不会让已经关联到该时间块的任务失效。

任务的执行场景是硬约束：“仅工作时间”只使用 `work` 块，“仅下班后”只使用 `home` 块，命名场景只使用对应的命名块；它们不会借用白天的“不限场景任务时间”块。只有任务自身选择“任意时间”时，才可以跨工作、下班后、命名和不限场景窗口安排。

调度流程（每次点击 `调度` 或增删改任务时执行）： 

1. **构建可用时间**：取当天启用的可用时间块，减去普通 Google Calendar 事件（受保护，不可修改），再裁掉当前时刻之前的部分。
2. **任务分类**：已完成任务按实际时间原样保留；已跳过任务不参与；日历中状态为 scheduled 的 Plan 事件回读后会保留其当前日历时间作为上次计划时间，用于时间轴显示、完成匹配和更新同一个 Calendar 事件，但不会默认视为硬固定任务。只有用户手动勾选"固定"并同步过的任务，回读后才继续硬固定在日历时间上。
2.5. **校验依赖图**：前置任务引用不存在时报告 `missing_dependency`，形成依赖环时报告 `dependency_cycle` 并停止调度。调度器不会忽略无效依赖；后续任务的最早开始时间是所有前置任务最后一个分段的结束时间。固定时间与依赖顺序互相矛盾时报告明确冲突。
3. **全局最小检查**：所有活动任务的最小时长之和大于可用时间总量时，报 `minimum_overflow` 冲突并停止。
3.5. **划分场景窗口**：按可用块的场景把时间分成窗口——所有 `work` 块构成"工作窗口"，所有 `home` 块构成"下班后窗口"。仅工作任务锁定到工作窗口，仅下班后任务锁定到下班后窗口，两个窗口的富余时间互不输送（工作任务延长不会挤占晚上的任务）。任意场景任务是"浮动任务"，需择优分配（见下）。各窗口独立完成第 4–6b 步。
3.6. **浮动任务择优**：任意场景任务对每个候选窗口各生成一份计划，比较全局总压缩量 `Σ(想要 − 实际)`，选冲突最少、总压缩最小的分配（浮动任务 ≤ 8 时枚举所有组合，> 8 时退化为按优先级贪心）。窗口在共享时间线上依次排布，因此即使不同场景的块在时钟上重叠也不会重复占用同一段时间。排布顺序为：`任意` 窗口最后（让受限场景任务先占位），其余窗口按容量从小到大——更受限（更小）的窗口先占位，避免"只有一段重叠时间可用"的窗口被范围更大的窗口抢光（例如自定义窗口 13:00–16:30 与工作窗口 10:10–16:30 重叠时，自定义窗口先安排）。
4. **计算实际时长（窗口内）**：先为窗口内每个任务保留最小时长；该窗口的剩余容量在弹性任务（想要 > 最小）之间按 `优先级 × 弹性空间` 加权分配，上限为想要时长。`最小 = 想要` 的任务不可压缩。
5. **放置固定任务**：固定任务的未来时段必须完整落在某个空闲块内，放置后从空闲块中扣除。
6. **放置弹性任务（约束紧的先选位置）**：窗口内放置顺序为——有截止时间的任务按截止时间从早到晚最先放；同级之间按优先级排序。优先级不决定任务在一天中的先后，只决定窗口稀缺时谁先挑位置、压缩时谁被保护。每个任务在候选块中按精力匹配度和顺序偏好评分选位：可拆分任务优先选能完整容纳的块，其次选拆分后剩余仍不小于最小分段的块，最后才允许留下无法放置的尾巴；不可拆分任务优先找能放下全部时长的块，否则放入能满足最小时长的最大块并截短。`minSegmentMinutes` 只防止拆分产生过碎片段；如果一个任务计算出的实际总时长本身小于 `minSegmentMinutes`，它可以作为一个完整短任务安排。
6a. **顺序偏好（软约束）**：每个任务有 `orderPreference` 属性（`morning` / `afternoon` / `evening` / `any`），默认由任务类型的昼夜节律决定（编码工作、复杂学习偏上午；打游戏、运动健身、绘画副业偏晚间；背单词、生活杂务、自定义不限）。偏好只是候选块评分的加分项：能满足就满足，不能满足绝不报错。
6b. **放置失败按缺口精确压缩（窗口内）**：如果某个任务连最小时长都放不下，调度器不会立刻报冲突，而是：计算缺口 → 找出同窗口内当前分配超过最小时长的任务作为"让渡者" → 把缺口按保护度（优先级）反比分摊给让渡者，保护度高的让得少 → 某个让渡者被压到最小时长时，剩余缺口由其他让渡者继续承担（即使其保护度更高）→ 扣减后重排。压缩逐轮收敛：一轮凑不齐缺口时先压下已有富余、再重试下一轮，直到放下或该窗口所有让渡者都到最小时长仍不够才报冲突。
7. **截止时间约束**：填写了截止时间的任务，其时段一律安排在截止时间之前；块内超出截止时间的部分不计入该任务的可用容量。用户手动勾选"固定"但固定时间在截止时间之后的，会报 `deadline_violation` 冲突并指明该任务，由用户决定改固定时间、改截止时间还是删除任务。普通回读 Plan 事件不是硬固定任务，会按截止时间和当前可用时间重新安排。
8. **冲突与部分安排**：只要所有任务都达到最小时长，理想时长没有排满也不作为用户警告；这只是正常压缩结果。调度结果内部可能标记为 `partial` 并在调试导出中保留剩余理想时长，页面不再显示“部分任务未完全安排”。只有某任务连最小时长都放不下时，才报 `placement_failure` 冲突，并指明该任务、计划分配时长、最小时长、实际能放入的分钟数，以及当时尝试过的兼容时间块。
9. **同步预览**：无冲突时生成对 Google Calendar 的创建/更新/删除操作预览，等待用户确认同步。

优先级公式：`重要性 × 10 + 紧迫度 × 6 + √想要时长 + 外部承诺 × 4`。紧迫度由截止时间距离决定（已过期 6，≤6 小时 5，≤24 小时 4，≤72 小时 2，更远 1，无截止 0）。

精力曲线（用于块评分）：8-12 点为高精力，12-14 点和 17-21 点为中精力，其余为低精力。任务的精力需求与时段精力越匹配，评分越高。

冲突面板会按优先级从低到高列出所有未完成任务，每个任务可直接 `编辑` 或 `删除并重排`。删除本地任务立即移除；删除已同步到日历的任务会先标记跳过，下次同步时删除对应日历事件。

## 调试导出

`复制调试信息` 按钮会把当天调度的完整输入输出序列化为 JSON 并复制到剪贴板，内容包括：计划日期、当前时间、可用时间块、受保护的日历事件、全部任务字段（含截止时间、场景、顺序偏好、固定/锁定状态）以及最近一次调度结果（含冲突详情）。遇到异常报错时点一下，把粘贴板内容发给助手即可复现分析。剪贴板不可用时会自动回退到隐藏文本框复制；两者都失败时报告会存入 `window.__planDebugReport` 供控制台手动复制。

## 时间轴视图与快捷输入

当天计划以左侧纵向时间轴、右侧详情面板展示。Plan 任务会显示为可选择的任务块；同一任务被拆成多段时，按时间顺序显示 `1/2`、`2/2` 一类的分段编号。普通 Google Calendar 事件会显示为灰色受保护块，只阻塞时间，不会被应用编辑或删除。点击任务块后可在右侧编辑、完成、删除/跳过并重排；点击普通日历块只显示只读说明。

时间轴会保留当前时间之前的上下文。已经完成的任务按实际开始/结束时间显示为完成色；预定时间已经过去但尚未完成的 Plan 任务会显示为“已错过”状态，而不是被隐藏或自动完成。点击“完成”时才会记录实际完成时间，并用当前时间重排后续任务。

完成是可撤销的。当天计划下方有一个“已完成”列表，列出当天所有已完成任务，每项带“恢复为未完成”按钮；已完成任务块的详情面板里也有同样的按钮。恢复会把任务退回未完成状态、清空实际时间并重新排入计划；已同步到日历的任务会在下次发布时把对应事件从“已完成”改回“计划中”。即使误点完成的是一个计划开始时间晚于当前时刻的任务（此时它不会显示在时间轴上），它仍会出现在“已完成”列表中，可以在那里恢复。

固定任务如果填写了固定开始时间和固定结束时间，保存时会用固定时间差自动覆盖 `想要时长` 和 `最小时长`。例如 `19:30 - 21:20` 会保存为 110 分钟。非固定任务仍然需要填写想要时长和最小时长。

截止时间字段旁的 `今日` 按钮会把截止日期填成浏览器本地今天；如果原本已有时间，会保留该时间，否则默认填 `23:59`。

## 本地运行

在项目根目录运行：

```bash
python -m http.server 5173
```

然后打开：

```text
http://localhost:5173
```

## 测试

运行：

```bash
npm test
```

## Google OAuth 设置

1. 打开 Google Cloud Console，并创建或选择一个项目。
2. 在该项目中启用 Google Calendar API。
3. 创建 OAuth Client，应用类型选择 Web application。
4. 在 Authorized JavaScript origins 中添加 GitHub Pages 来源，例如 `https://<user>.github.io`。
5. 本地测试时，在 Authorized JavaScript origins 中添加 `http://localhost:5173`。
6. 将生成的 OAuth Client ID 填入应用并保存。

应用使用的 Google Calendar scope 是：

```text
https://www.googleapis.com/auth/calendar.events
```

## 日历数据规则

- `读取并显示日历` 是只读操作：它只拉取当天主日历事件，在页面时间轴中展示，并把普通日历事件作为受保护时间块参与调度。
- `发布计划到 Google Calendar` 才会写入主日历：它只会创建、更新或删除 Plan 自己管理的 `[Plan]` 事件。
- 普通 Google Calendar 事件没有 `PLAN_META`，应用只把它们视为受保护的不可用时间。
- 应用只会创建、更新、删除元数据有效的 `[Plan]` 事件。
- 计划任务属性保存在事件 description 的 JSON 中。运行时字段（如 `autoFixed`、`plannedStart`、`plannedEnd`、`calendarEventId`）不会再写入 description。
- 一个可拆分任务在 Google Calendar 中对应多个事件，但网页端始终把它们合并为一个逻辑任务进行调度和编辑；事件 ID 与分段 ID 只用于逐段完成和同步。重新调度改变分段时间后，编辑仍按逻辑任务 ID 生效，并在发布时更新原有事件而不是制造重复任务。
- 旧版本已经写入 `autoFixed: true` 且同时污染了 `fixed: true` 的事件，回读时会按非手动固定任务处理；发布一次后，对应事件会被更新为干净元数据。
- 访问令牌只保存在浏览器内存中，不写入 `localStorage`。

## GitHub Pages 部署

1. 将代码推送到 GitHub 仓库。
2. 在仓库 Settings 中打开 Pages。
3. Source 选择要发布的分支，目录选择项目所在目录或根目录。
4. 保存 Pages 设置，等待 GitHub 生成站点地址。
5. 将生成的站点来源添加到 Google OAuth 的 Authorized JavaScript origins 中。
6. 使用 GitHub Pages 地址打开应用，并在应用中保存 OAuth Client ID。

## GitLab Pages 部署

项目已包含 `.gitlab-ci.yml`。推送到 GitLab 后，默认分支会自动执行：

1. 使用 Node.js 运行 `npm test`。
2. 将 `index.html` 和 `src/` 复制到 `public/`。
3. 通过 GitLab Pages 发布静态站点。

部署步骤：

1. 在 GitLab 创建一个仓库。
2. 将本项目推送到该仓库的默认分支。
3. 等待 GitLab CI/CD pipeline 完成。
4. 在 GitLab 项目中打开 Deploy -> Pages 查看站点地址。

普通项目的 Pages 地址通常是：

```text
https://<namespace>.gitlab.io/<project-name>/
```

如果你想使用根域名形式：

```text
https://<username>.gitlab.io/
```

GitLab 项目名需要是：

```text
<username>.gitlab.io
```

部署到 GitLab Pages 后，也要把对应 origin 加到 Google OAuth 的 Authorized JavaScript origins。普通项目示例：

```text
https://<namespace>.gitlab.io
```

注意这里只填写 origin，不包含 `/<project-name>/` 路径。

## 数据安全

任务名称可能会同步到 Google Calendar 事件中。涉及敏感公司项目、客户名称、内部代号或个人隐私时，建议避免填写真实名称，或先进行匿名化处理。
